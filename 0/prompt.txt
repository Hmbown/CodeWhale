## Critical

**1. macOS screenshot driver assumes a single display; breaks (or silently mis-targets) on any multi-monitor Mac**
`crates/computer-use/src/drivers/macos.rs:469-499` (`MacDriver::screenshot`)

```rust
let out = process::run(&amp;screencapture, &amp;["-x", "-C", "-t", "png", &amp;path_str], ...);
```
No `-m` (main-monitor-only) or `-D &lt;display&gt;` flag is passed. Per Apple's own `screencapture` man page, when more than one display is attached and a single output path is given, the tool writes **one file per screen** (only the first display maps to the literal filename you passed; the rest get suffixed names that this driver never reads). `MacDriver`'s whole coordinate model (`to_points`, `scale()`) is anchored to the **main** display's logical size/backing scale, fetched once in `MacDriver::new()` via `CGMainDisplayID()`. If the file written to `path` happens to correspond to a non-main display (which display ends up first is not something this code controls), every subsequent click/move/drag will be computed against the wrong display's geometry, sending clicks to the wrong screen or to nonsensical device pixels.

Confidence: 82 — confirmed via Apple's documented `screencapture` behavior ("1 file per screen" without `-m`), and the code path is unconditional (any dual/multi-monitor Mac hits it, not an edge case). This wasn't caught by the design's live smoke test because it only ran on a single-display host.

Fix: pass `-D &lt;n&gt;` for the specific display index, or (simplest, matches the rest of the coordinate model) add `-m` to force main-monitor-only capture:
```rust
&amp;["-x", "-C", "-m", "-t", "png", &amp;path_str]
```

**2. `parse_bounds` silently drops the sign of negative coordinates (Android + HarmonyOS UI-tree)**
`crates/computer-use/src/drivers/android.rs:561-572` (`parse_bounds`, also reused by `harmony.rs:508` via `crate::drivers::android::parse_bounds`)

```rust
pub fn parse_bounds(value: &amp;str) -&gt; Option&lt;(u32, u32, u32, u32)&gt; {
    let nums: Vec&lt;u32&gt; = value
        .split(|c: char| !c.is_ascii_digit())
        .filter(|s| !s.is_empty())
        .filter_map(|s| s.parse().ok())
        .collect();
    ...
}
```
`uiautomator dump` (and HarmonyOS `dumpLayout`) commonly report negative bounds for elements that are partially scrolled off-screen, e.g. `bounds="[-10,-50][1080,200]"`. Splitting on "not an ASCII digit" treats `-` purely as a delimiter, so `-10` is parsed as `10` — the magnitude survives but the sign is lost, not merely rejected. This silently produces a wrong `(left, top, right, bottom)` tuple (and therefore a wrong `center()`) for any node with a negative bound, rather than erroring or filtering the node out. Since `is_interesting()` doesn't check visibility, such a node can still be surfaced to the model in `computer_ui_tree` output with a plausible-looking but incorrect frame-space center, leading the model to tap the wrong location.

Confidence: 82 — verified by hand-tracing the split/parse logic (not dependent on an external doc), and negative bounds for off-screen/partially-scrolled list items are a known, common occurrence in real `uiautomator`/`dumpLayout` output, not a contrived edge case.

Fix: parse each `[l,t]`/`[r,b]` pair with a proper signed-integer scanner (e.g. regex `-?\d+` or manual sign handling before the digit run) and switch the tuple to `i32` (or clamp negatives to 0 if the rest of the pipeline truly requires `u32`, but do so explicitly rather than by accident).

- `crates/computer-use/src/drivers/macos.rs:238-251` (`type_unicode`): text is UTF-16-encoded then chunked with `.chunks(16)` with no awareness of surrogate-pair boundaries. If a non-BMP character (e.g. an emoji) happens to land exactly on a 16-code-unit chunk boundary, its surrogate pair would be split across two `CGEventKeyboardSetUnicodeString` calls, corrupting that character. This is real but low-probability (needs a surrogate pair to straddle exactly index 16, 32, 48…), so I'm not confident enough to rate it ≥80, but it's cheap to fix by chunking on `char` boundaries instead of raw `u16` counts.
